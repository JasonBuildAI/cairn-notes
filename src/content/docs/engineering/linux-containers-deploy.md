本机运行和线上运行之间，隔着机器、权限、网络和发布流程。这一页只保留理解部署链路必需的抽象。

## 1. Linux 上先看懂四个东西

| 抽象 | 要回答的问题 | 常用命令 |
| --- | --- | --- |
| 进程 | 谁在运行，占了多少资源 | `ps`、`top`、`kill` |
| 文件 | 配置、日志、模型权重放在哪里 | `ls`、`df`、`du`、`tail` |
| 权限 | 谁能读、写、执行 | `ls -l`、`chmod`、`chown` |
| Socket | 进程监听哪个地址和端口 | `ss -ltnp` |

进程收到 `SIGTERM` 时应停止接新请求、处理完或取消进行中的任务、关闭连接，再退出。直接 `kill -9` 不会给清理机会，可能留下临时文件和半完成状态。

## 2. 容器不是轻量虚拟机

| 对比 | 虚拟机 | 容器 |
| --- | --- | --- |
| 隔离对象 | 完整操作系统 | 进程、文件系统、网络等内核资源 |
| 启动 | 较慢 | 较快 |
| 交付物 | 磁盘镜像 | 镜像 + 运行时配置 |
| 安全边界 | 通常更强 | 依赖内核、配置与运行时 |

容器把应用和依赖打包成不可变镜像。镜像由层组成，基础层可以复用；运行时的配置和数据应挂在镜像外。

```dockerfile
FROM node:24-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .
USER node
CMD ["node", "server.js"]
```

要检查的不是“能构建”，而是：

- 是否以非 root 用户运行。
- 镜像里是否混进了密钥和本地文件。
- 是否有健康检查、资源限制和日志输出。
- 基础镜像与依赖是否固定到可追溯版本。
- 容器停止时能否优雅退出。

Docker Compose 用一个文件描述多个服务、网络、卷和启动依赖，适合本地联调和较小部署；它不是完整的集群调度器。涉及多机调度、滚动升级和自愈时再考虑 Kubernetes，不要为了“服务多”就跳过对单机部署的理解。

## 3. 构建一次，部署同一个产物

```
提交
  │
  ├─► 安装依赖
  ├─► 静态检查 / 单元测试
  ├─► 构建产物或镜像
  ├─► 扫描依赖与镜像
  ├─► 部署到测试环境
  ├─► 自动冒烟验证
  └─► 上线 / 可回滚
```

CI 负责把输入变成可追踪的产物；CD 负责把同一个产物送到环境里。不要在服务器上重新拉源码、重新安装并现场构建，否则线上运行的版本很难复现。

发布时至少记录：提交、镜像摘要、配置版本、部署时间和操作者。回滚应指向旧产物，而不是“再改一次代码试试”。

## 4. CI/CD 的检查点

- 构建失败要阻断发布，而不是只发一条通知。
- 生产密钥由 CI/CD 的密钥存储注入，不写进日志和镜像。
- 数据库迁移、配置变更和代码发布要考虑顺序与兼容性。
- 部署后验证真实入口，而不只看容器进程状态。
- 失败发布必须能停止、回退，并保留现场证据。

## 5. Kubernetes 在哪里

Kubernetes 适合多服务、多副本、需要自动调度和滚动发布的场景。它不是“上线的默认答案”。

| 对象 | 作用 |
| --- | --- |
| Pod | 一个或多个紧密关联的容器 |
| Deployment | 管理副本与滚动更新 |
| Service | 给一组 Pod 提供稳定访问 |
| Ingress | 把外部流量路由到 Service |

控制面负责声明式状态与调度，节点上的 kubelet 和容器运行时负责真正拉起容器。排障时要先分清是“控制面没接受配置”“Pod 没被调度”“容器启动失败”，还是“服务通了但入口没路由”。

单机小服务用托管平台或一台服务器加反向代理可能更简单。引入 K8s 前，先确认团队能维护集群、网络、存储、权限和升级。

## 6. AI 推理服务的额外差异

- 首个 token 的等待时间通常比完整响应时间更影响体验。
- 长连接和流式响应要求代理、超时、缓冲策略都正确配置。
- 模型权重可能很大，镜像构建、启动和磁盘容量要单独规划。
- 有 GPU 时，调度、驱动、显存和并发限制都是部署参数。
- readiness 应表示“能接请求”，不只是“进程还活着”。
- 模型调用要有超时、限流和熔断，不能让一个慢请求占满所有工作线程。

上线前的底线是：知道服务在哪台机器上、运行哪个产物、配置来自哪里、失败时从哪里看证据、怎样回滚。
