---
title: 可观测性与故障处理
description: 用日志、指标和 trace 证明系统发生了什么，并把故障变成可复用的经验。
---

可观测性不是“日志很多”，而是能否在不加代码的情况下回答：哪个用户、哪个请求、哪一层、为什么失败。AI 服务还多了模型延迟、token 用量和工具调用这些变量。

## 1. 先定义什么叫正常

选几个和用户直接相关的指标：

| 指标 | 示例问题 |
| --- | --- |
| 可用性 | 请求成功比例是多少？ |
| 延迟 | 首 token 和完整响应各等了多久？ |
| 错误率 | 4xx、5xx、超时、限流分别多少？ |
| 饱和度 | 队列、连接、显存、上下文窗口是否接近上限？ |
| 成本 | 每次请求用了多少 token、多少钱？ |

SLI 是实际测到的指标，SLO 是希望达到的目标。不要只监控 CPU；CPU 不高但用户等 30 秒，仍然是故障。

## 2. 三类信号各管什么

| 信号 | 擅长回答 | 注意 |
| --- | --- | --- |
| 指标 Metrics | 趋势、告警、容量 | 聚合后可能看不到单个请求 |
| 日志 Logs | 具体错误与上下文 | 容易过多，需结构化字段 |
| Trace | 一次请求经过哪些服务和耗时 | 需要传播 request ID |

一次 AI 请求至少应能拆出：入口排队、鉴权、上下文组装、模型首 token、模型生成、工具执行、持久化和流式回传。否则延迟升高时只能猜。

## 3. 日志要结构化，也要克制

推荐字段：时间、级别、service、request ID、会话 ID、路由、状态码、耗时、模型名、错误分类、重试次数。用户内容和完整提示词默认不记录；需要时脱敏、采样并限制保留时间。

```text
level=error request_id=req_123
route=/v1/chat model=... stage=model
error=timeout elapsed_ms=30000
```

日志里不要放 API Key、Cookie、Authorization 头、完整文件内容和个人数据。日志系统本身也要有访问控制。

## 4. 告警要看用户影响

好的告警满足：可行动、指向明确、不会因为正常波动反复触发。

- 告警“错误率超过阈值”，而不是“某个 pod 重启了一次”。
- 告警“首 token 延迟持续超标”，而不是“GPU 使用率 80%”。
- 每个告警附 runbook：先看什么、如何缓解、找谁。
- 告警风暴时先合并根因，不要让所有下游同时叫人。

## 5. 事故处理顺序

1. **发现**：告警、用户反馈或自动探测。
2. **分级**：影响多少用户，是否涉及数据和安全。
3. **止血**：限流、回滚、切流、关闭非核心功能。
4. **沟通**：明确负责人、时间线和当前影响。
5. **恢复**：验证真实入口和关键路径，不只验证进程。
6. **复盘**：找系统性原因，补监控、测试或流程。

复盘不追责个人，但要区分“触发事件”和“为什么系统无法承受”。例如模型 API 限流是触发点，缺少降级、队列和告警才是系统问题。

## 6. AI 服务常见故障

| 现象 | 先看什么 | 可能方向 |
| --- | --- | --- |
| 首 token 很慢 | 队列、上游模型、流式代理 | 并发过高、缓冲、超时 |
| 完整响应很慢 | token 数、工具耗时 | 生成长、循环、外部依赖 |
| 大量 429 | 上游配额、重试策略 | 限流、退避、租户配额 |
| 上下文溢出 | 消息数、截断策略 | 压缩、摘要、分段 |
| 工具失败 | 参数、权限、超时 | schema 校验、隔离、重试 |
| 沙箱残留 | 生命周期、清理任务 | 异常路径未回收 |
| 成本突然升高 | token、模型版本、重试 | 缓存失效、失控循环 |

## 7. 一页 runbook

```text
服务：
用户影响：
关键指标与正常范围：
最近一次发布：
入口与依赖：
立即止血动作：
回滚方式：
升级联系人：
证据位置：
```

这份模板和最小复现记录一起使用。目标是让下一个值班的人不需要从零理解整个系统。
