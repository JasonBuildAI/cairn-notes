title: 模型选型、微调与部署
description: 从能力、成本和风险选择模型，并把评测、推理部署与版本治理接成闭环。
---

模型选型不是“榜单第一就选它”。同一个模型在聊天、代码、结构化输出、长文档和多模态任务上的表现可能完全不同；生产系统还要考虑延迟、成本、数据边界和可替换性。

## 1. 选型先写约束

| 维度 | 要问什么 | 常见取舍 |
| --- | --- | --- |
| 任务质量 | 正确性、格式、多语言、工具调用 | 大模型通常更强，但更慢更贵 |
| 输入输出 | 文本、图片、音频、视频、长文档 | 多模态与长上下文增加成本 |
| 延迟 | 首 token、完整响应、P95 | 流式改善体感，不降低总时长 |
| 吞吐 | 并发、批量、速率限制 | 自建可控制，但需要运维和容量 |
| 上下文 | 最大 token、有效利用率 | 窗口大不等于所有内容同样有效 |
| 部署 | 云 API、私有化、边缘 | 数据 residency、网络和合规 |
| 成本 | 输入/输出 token、缓存、GPU 小时 | 最便宜不等于总成本最低 |
| 生态 | 工具调用、结构化输出、微调、版本 | 锁定风险与迁移成本 |

先做一个覆盖真实任务的小型评测集，再用候选模型盲测。选型记录应包含版本、参数、提示、样本、指标和失败案例，而不是只留一句“试过，比较好”。

## 2. 推理系统发生了什么

生成式模型推理大致分为：

1. **Prefill**：处理输入上下文，填充 KV cache。
2. **Decode**：逐个生成 token，每次都要读取模型权重和缓存。
3. **采样与停止**：应用 temperature、top-p 和停止条件。

长上下文主要增加 prefill 成本，长输出主要增加 decode 成本。批处理能提高 GPU 利用率，但可能增加单请求等待；KV cache 能减少重复计算，但占显存。量化降低显存和带宽需求，却可能影响质量，需要在自己的任务上复测。

自建推理要估算显存、并发、吞吐和故障转移；使用云 API 则要处理速率限制、重试、超时和供应商版本变化。无论哪种，都建议通过统一的模型网关接入，避免业务代码散落各家 SDK。

## 3. 微调不是默认答案

按改动程度从轻到重：

| 方案 | 改动 | 适合 |
| --- | --- | --- |
| 提示与上下文 | 规则、示例、检索 | 快速迭代、知识更新、行为约束 |
| RAG | 外部知识与引用 | 私有、变化快、需要权限的资料 |
| LoRA / PEFT | 训练少量适配参数 | 固定风格、领域格式、成本较低 |
| 全量微调 | 更新更多参数 | 数据充分、任务稳定、资源足够 |
| 偏好对齐 | SFT 后使用偏好数据 | 行为风格、安全边界、复杂偏好 |

LoRA 用低秩矩阵近似参数更新，训练和存储成本更低，但不会自动补足知识或解决检索问题。微调需要训练集、验证集、去重、脱敏和灾难性遗忘检查。上线前要比较基础模型与微调模型的通用能力，避免“领域好了一点，其他都退化”。

## 4. 评测要接近真实工作

评测至少分三层：

| 层 | 例子 | 作用 |
| --- | --- | --- |
| 能力 | 分类、抽取、代码、数学 | 判断模型是否具备基本能力 |
| 任务 | 真实输入、工具链、引用 | 判断能否完成业务目标 |
| 产品 | 采纳率、追问、延迟、成本 | 判断是否值得上线 |

样本要来自真实分布，并保留困难集、无答案集和安全集。LLM-as-a-judge 适合扩展评测，但裁判本身会被顺序、长度和措辞影响，必须用人工标注校准。线上好评和点赞有选择偏差，不等于总体质量。

每次变更——模型、提示、检索、工具或参数——都应在同一评测集上回归。记录版本和环境，否则无法解释分数变化。

## 5. 部署与版本治理

一个可运营的模型服务至少需要：

- 模型与提示版本注册；
- 请求级 trace 和 token/成本记录；
- 超时、重试、限流和熔断；
- 灰度、影子流量和快速回滚；
- 结构化输出校验与安全过滤；
- 数据保留、租户隔离和访问审计；
- 失败样本收集与评测集更新。

模型供应商升级可能改变行为，所以“模型别名”不能替代版本固定。需要允许灰度到新版本，并在质量、延迟或成本异常时回到旧版本。

## 6. 成本不只是一张 token 账单

总成本包括：

- 输入与输出 token；
- 检索、embedding、rerank；
- 工具调用和第三方 API；
- GPU 空闲、冷启动、存储和网络；
- 评测、人工审核和故障处理。

优化时先找到主要成本项。常见手段包括缓存稳定前缀、限制输出、先用小模型路由、按任务选择模型、压缩上下文和批处理。不要为了省几毛钱牺牲关键任务正确性，也不要用“平均成本”掩盖长尾请求。

## 7. AI 原生应用的产品检查

AI 功能需要额外的交互约束：

- 明确显示能力边界和不确定性；
- 关键结论提供证据或来源；
- 生成结果可编辑、可撤销、可重新生成；
- 长任务显示进度，允许取消；
- 自动操作有审批和预算；
- 失败时说明是模型、网络、权限还是输入问题；
- 不用流畅的语言掩盖缺失的数据。

AI 产品最危险的设计，是让用户无法判断系统到底做了事实查询、猜测，还是已经执行了外部操作。

## 8. 生命周期检查表

1. 选型是否基于自己的任务集，而不是只看公开榜单？
2. 首 token、完整响应、并发和成本是否分别测量？
3. 数据和权限是否允许送入外部模型？
4. 微调是否解决了提示和 RAG 解决不了的问题？
5. 评测集是否覆盖困难、无答案和安全场景？
6. 模型、提示、索引和工具版本能否一起回滚？
7. 线上失败是否能进入下一次评测，而不是只留在日志里？
