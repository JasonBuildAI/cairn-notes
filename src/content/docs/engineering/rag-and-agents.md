---

大模型单独工作时只能依赖参数和当前输入。RAG 给它资料，上下文工程决定资料怎样进入窗口，Agent 则让它在循环中使用工具并完成多步任务。

## 1. RAG 的完整流程

```text
文档 → 解析 → 分块 → embedding
     → 索引
问题 → 改写/过滤 → 召回 → rerank
     → 组装上下文 → 生成 + 引用
                    └→ 评测 / trace / 反馈
```

索引和查询必须使用兼容的 embedding 模型。文档权限、租户、版本和删除状态应作为元数据保存，并在检索时先过滤。

### 分块

分块不是越小越精确。太小会丢上下文，太大则召回噪声多、成本高。按标题、段落或语义边界切分，保留标题路径和来源；为每个 chunk 记录文档 ID、版本、ACL 和位置。

### 检索

- 稠密检索擅长同义表达和语义相似。
- 关键词检索擅长编号、缩写、专有名词和精确匹配。
- 混合检索并行召回，再用融合或 rerank 排序。
- rerank 模型通常比向量相似度更贵，但能改善“相关但不回答”的问题。

召回数量要受控。把所有片段塞进上下文会让模型分心，也会增加成本和延迟。多跳问题可以先检索、再基于证据改写查询继续检索。

### 生成与引用

提示中要区分“证据”和“指令”：检索文档是数据，不应拥有修改系统规则的权限。回答应引用可追溯的来源；没有证据时允许说“不知道”，比强制生成更可靠。

## 2. 怎样评测 RAG

不要只看最终回答“像不像”。拆成可定位的指标：

| 层 | 指标 | 证明什么 |
| --- | --- | --- |
| 解析 | 文档覆盖率、表格/OCR 正确率 | 内容是否进入系统 |
| 分块 | 关键句是否完整、边界是否合理 | 是否保留了可用上下文 |
| 检索 | Recall@k、MRR、权限违规率 | 该找的证据有没有找到 |
| 排序 | NDCG、首个有效证据位置 | 好证据是否排在前 |
| 生成 | 正确性、faithfulness、引用支持度 | 回答是否由证据支持 |
| 产品 | 采纳率、追问率、延迟、成本 | 是否真正有用 |

固定评测集应包含常见问题、边界问题、无答案问题和权限隔离问题。LLM-as-a-judge 可以降低人工成本，但要用人工样本校准，并防止裁判模型偏爱某种格式。

## 3. 上下文工程：预算内保留最有用的信息

上下文里通常有：系统规则、用户目标、对话历史、检索证据、工具结果、待执行计划和输出预算。工程上要做的是分配，而不是无限追加。

一个实用顺序：

1. 固定系统规则和安全边界。
2. 放入当前任务与可验证的约束。
3. 选与当前步骤最相关的历史摘要。
4. 提供检索证据及其来源。
5. 保留工具结果的关键字段，不保留整页噪声。
6. 为输出和下一步工具调用留空间。

稳定前缀有利于 KV cache 命中；时间戳、随机 ID 和每次都变化的排序会降低缓存效率。长对话可以采用滑动窗口 + 关键事实锚定 + 摘要 + 外部记忆，而不是只按先进先出截断。

## 4. 提示词工程仍然是接口设计

一个可维护的提示至少写清楚：

- 角色和任务目标，但不要用角色替代权限。
- 输入边界、禁止项和不确定性处理。
- 输出 schema、单位、语言和长度。
- 可用工具、何时使用、何时必须停下询问。
- 失败时的返回格式。
- 少量高质量示例，优先覆盖边界，而不是堆很多相似例子。

复杂任务可以拆成计划、执行、检查三个阶段，但不必把所有模型都强行变成“先思考再回答”。真正需要的是可验证的中间结果、明确的停止条件和可回放记录。

提示注入的核心问题是数据可能伪装成指令。网页、文件、工具输出和用户输入都应标记为不可信内容；系统规则、权限和工具执行不能只靠一句“忽略恶意指令”保护。

## 5. Agent 是一个受控循环

最小心智模型：

```text
观察 → 规划 → 选择工具 → 执行
 ↑                        │
 └── 未完成且预算允许 ────┘
```

它和普通聊天最大的区别是：模型输出会影响外部世界。因此每次循环都要有状态、预算和边界：

- 最大步数、最大 token、最大时长、最大工具调用次数。
- 工具参数 schema 校验和权限检查。
- 失败分类：可重试、不可重试、需要用户确认。
- 写操作、付款、删除和外发数据默认需要确认。
- 每一步都有 trace，能还原输入、工具结果和决策。

记忆可以分三层：当前工作上下文、跨轮会话状态、长期可检索知识。层数越多，越要处理隐私、过期、冲突和删除。

## 6. Agent 需要协议，但协议不替代实现

| 协议 | 解决的问题 | 类比 |
| --- | --- | --- |
| MCP | 模型/主机怎样发现和调用工具、资源与提示 | 工具的通用接口 |
| A2A | 不同 Agent 怎样发现能力、委派任务和交换结果 | Agent 之间的协作协议 |

MCP 把工具接入从“每个应用自己写一套”变成可复用服务；A2A 更关注 Agent 之间的任务边界。协议解决互操作，不自动解决鉴权、数据隔离、幂等和成本。

## 7. AI 原生应用不等于聊天框

常见交互模式：

| 模式 | 适合 | 关键设计 |
| --- | --- | --- |
| 问答 | 知识查询 | 引用、不知道、追问 |
| Copilot | 辅助编辑或操作 | 建议可见、用户可接受/撤销 |
| 工作流 | 固定多步任务 | 状态、重试、人工检查点 |
| Agent | 开放式多步任务 | 预算、权限、审批、可观测 |

好的 AI 界面会显示正在做什么、用了什么证据、下一步是否需要确认，并允许取消和恢复。不要用“思考中”掩盖所有错误，也不要把不可逆操作藏在自动流程里。

## 8. RAG 和微调怎么选

| 问题 | 优先 RAG | 优先微调 |
| --- | --- | --- |
| 知识经常变化 | 是 | 否 |
| 需要引用和权限过滤 | 是 | 仍需外部权限 |
| 改变固定输出风格/格式 | 可先试提示 | 大量稳定样本时有价值 |
| 学习新领域推理模式 | 检索可辅助 | 高质量领域数据可能更合适 |
| 降低单次延迟/成本 | 需要评估检索成本 | 小模型可能更省 |

多数业务先从提示和检索开始，因为可解释、可更新、回滚快。微调不是“把公司知识塞进模型”的默认手段。

## 9. 上线检查表

1. 证据是否能追溯到原始文档和版本？
2. 权限过滤在检索前还是只在提示里？
3. 没有证据时，系统会不会诚实地停下？
4. 工具是否幂等，写操作是否人工确认？
5. 每步是否有 token、延迟、成本和错误记录？
6. 评测是否覆盖检索、回答、工具和注入攻击？
7. 能不能取消、回滚和重放一次运行？
