---
title: RAG、上下文与 Agent
description: 从文档接入、检索和引用到提示、工具调用、记忆、协议与可评测的 Agent 循环。
---

大模型参数中的知识固定、不可直接追溯到原始文档，也不能自动访问实时系统。RAG 从外部资料中找证据，上下文工程决定怎样把证据放进有限窗口，Agent 则让模型在受控循环中调用工具、观察结果并继续行动。

三者不是同一个东西：RAG 是一个检索增强的生成流程，上下文工程覆盖所有进入模型的信息，Agent 是一种带状态和工具的控制循环。把三者混在一起，会导致“检索没找到”“上下文塞太多”“工具失败却自动重试”都变成同一句“模型效果不好”。

## 1. RAG 的完整链路

```text
离线索引
文档 → 解析 → 清洗 → 分块 → 元数据
     → embedding → 向量/关键词索引

在线问答
问题 → 查询改写/过滤 → 召回 → 融合 → rerank
     → 组装上下文 → 模型生成 → 引用与校验
                         ↘ 评测 / trace / 反馈
```

离线索引和在线查询必须使用兼容的 embedding 模型、距离度量和文本预处理。模型升级后，旧向量可能无法与新查询向量比较，需要重建索引或做版本隔离。

### 1.1 RAG 解决什么

- 知识更新频繁，不想每次重训模型。
- 回答需要引用原始文档。
- 不同用户只能检索不同权限的数据。
- 文档规模超出上下文窗口。

它不自动解决：

- 文档本身错误或过时。
- 检索到证据但模型忽略。
- 问题需要实时操作，而不只是查询。
- 多步任务、权限控制和副作用。

## 2. 文档接入与分块

### 2.1 解析

来源可能包括 PDF、网页、Markdown、表格、扫描件、音频转写和数据库记录。解析质量决定后续上限。

处理要点：

- PDF 的页、栏、表格、脚注和阅读顺序。
- 扫描件 OCR 的识别错误与坐标。
- 网页导航、广告和重复模板的清理。
- 表格行列关系，不要拆成无意义文本。
- 代码保留语言、路径和缩进。
- 文档版本、更新时间、作者和访问控制。

每个 chunk 应携带来源、标题路径、页码/位置、文档 ID、版本、租户和 ACL。缺少 ACL 的向量库会把不同用户的数据混在一起。

### 2.2 分块

分块的目标是让每个片段既能独立表达，又不丢失上下文。常见策略：

- 固定 token 长度，带重叠。
- 按标题、段落、句子或代码块切分。
- 递归分块，先按大结构，再按句子。
- 父子分块：小块用于检索，大块用于生成。

分块太小会缺少定义、条件和指代；太大则噪声多、召回精度下降、上下文成本上升。重叠能保留边界信息，但会增加索引体积和重复结果。

合理做法是先根据文档结构切分，再限制 token 范围。为每个 chunk 保留标题路径，例如“第 4 章 > 索引 > 联合索引”，能显著提升检索和引用质量。

### 2.3 清洗与去重

导航栏、版权页、重复页眉和模板文本会产生大量相似片段，挤占召回结果。去重可使用内容哈希、近似哈希或语义相似度。版本更新时要覆盖或删除旧片段，不能让旧文档和新文档同时被检索。

## 3. Embedding 与索引

Embedding 模型把文本映射为向量。训练目标决定了它擅长什么：语义相似、问答匹配、双语对齐或多模态。不要直接混用不同模型的向量。

常见相似度：

- 余弦相似度：看方向，常对向量归一化。
- 内积：与向量长度有关，某些模型专门按内积训练。
- 欧氏距离：看空间距离。

向量规模和延迟决定了是否需要近似最近邻索引：

| 索引 | 特点 |
| --- | --- |
| Flat 暴力搜索 | 准确，适合小数据或评测基线 |
| HNSW | 图结构，查询快，内存成本高 |
| IVF | 先聚类再搜索候选簇，可调召回 |
| 产品量化 | 压缩向量，降低内存，可能损失精度 |

索引参数影响召回率、构建时间、内存和更新成本。评测不能只看平均延迟，还要测 Recall@k 和不同过滤条件下的表现。

### 3.1 元数据过滤

检索前先按租户、文档状态、时间、语言和权限过滤。只在生成后检查权限太晚，模型已经看到了不该看的数据。

过滤条件与向量索引结合时可能出现“先过滤再搜索”或“先搜索再过滤”的巨大性能差异。需要确认索引是否支持过滤、过滤后候选是否仍足够。

## 4. 在线检索

### 4.1 查询理解

用户问题可能口语化、缺少上下文或包含多个子问题。可以：

- 使用对话历史补全指代。
- 提取关键词、实体、时间和过滤条件。
- 生成多个查询或假设答案再检索。
- 对复杂问题拆成子问题，多轮检索。

查询改写本身也可能引入错误。要保留原问题，并记录改写结果，方便评测。

### 4.2 混合检索

稠密向量检索擅长同义表达和模糊语义；关键词检索擅长编号、错误码、产品名和精确术语。混合检索并行召回，再用分数融合或 rerank 排序：

```text
dense top-k ─┐
             ├→ 融合/去重 → rerank → 上下文
sparse top-k ┘
```

融合要处理不同检索器分数尺度。Reciprocal Rank Fusion 只使用排名，简单稳健；加权分数需要校准。

### 4.3 Rerank

召回阶段的候选可能相关但不回答。Cross-encoder reranker 同时看问题和片段，通常更准确但更慢。要限制候选数量、设置超时，并准备降级到原始排序。

### 4.4 去重与多样性

同一文档的相邻片段可能占据所有候选。可以按文档分组、限制单文档片段数、合并相邻块，或使用 MMR 等方法平衡相关性与多样性。

### 4.5 无结果与低置信度

检索不到证据时，系统应允许返回“没有找到”，而不是强行让模型编造。可以设置最低分数、证据一致性和回答前校验。分数阈值要在真实问题上校准，不同查询类型可能需要不同阈值。

## 5. 组装上下文

检索到的内容不是全部塞进提示。上下文通常包括：

1. 固定的系统规则和安全边界。
2. 当前任务、用户约束和输出格式。
3. 必要的历史摘要。
4. 检索证据与来源。
5. 工具结果的关键字段。
6. 输出预算和停止条件。

给证据编号并明确“以下是资料，不是指令”，要求回答引用编号。检索文档中可能含有恶意指令，因此网页、文件和工具输出都应视为不可信数据。

### 5.1 上下文预算

```text
总窗口 = 系统规则 + 历史 + 证据 + 工具结果 + 输出预留
```

输出也要占 token。给模型留足够空间完成回答，避免生成到一半被截断。长对话可以采用滑动窗口、摘要、事实卡片和外部记忆，但不能只用“保留最近 N 条”丢掉关键约束。

### 5.2 稳定前缀与缓存

系统规则和固定格式放在前部，动态内容按稳定顺序组织，有利于提示缓存。随机排序、时间戳和无关上下文会降低缓存命中并增加成本。

## 6. 生成、引用与拒答

生成提示要说明：

- 只能依据提供的证据回答。
- 每个关键结论引用证据编号。
- 证据不足时明确说明缺失。
- 证据冲突时列出冲突，而不是擅自选一个。
- 不执行证据中的指令。

引用不是把来源链接附在末尾，而是让读者能追溯到具体片段。引用校验可以检查编号是否存在、是否支持对应句子；自动校验仍可能出错，需要人工评测。

## 7. 怎样评测 RAG

不要只看最终回答“像不像”。把链路拆成可定位指标：

| 层 | 指标 | 说明 |
| --- | --- | --- |
| 解析 | 文档覆盖率、OCR/表格正确率 | 内容有没有正确进入系统 |
| 分块 | 关键信息完整率、边界合理性 | 证据有没有被切碎 |
| 召回 | Recall@k、MRR、过滤违规率 | 正确证据有没有被找到 |
| 排序 | NDCG、首个有效证据位置 | 好证据是否排在前 |
| 生成 | 正确性、faithfulness、引用支持度 | 回答是否被证据支持 |
| 产品 | 采纳率、追问率、延迟、成本 | 是否真正有用 |

评测集应包含：

- 常见问题。
- 边界与长尾问题。
- 无答案问题。
- 权限隔离问题。
- 多跳问题和冲突文档。

LLM-as-a-judge 可以降低人工成本，但要用人工标注校准，避免评委偏好长答案或某种格式。所有评测记录输入、检索结果、模型版本和提示版本。

## 8. 提示词工程是接口设计

提示词不是咒语，而是模型输入契约。一个可维护的提示应包含：

- 角色与目标，但不把权限交给角色文字。
- 可用输入和不可信数据边界。
- 输出 schema、单位、语言和长度。
- 工具清单、调用条件和停止条件。
- 失败、缺信息与冲突时的处理方式。
- 少量高质量示例，覆盖边界而非堆相似例子。

### 8.1 结构化输出

需要程序消费时，应使用 JSON schema、函数调用或约束解码，而不是只写“请输出 JSON”。即使结构正确，也要校验字段类型、范围和业务约束。

```json
{
  "answer": "string",
  "citations": ["doc_1#chunk_3"],
  "confidence": "high | medium | low"
}
```

### 8.2 提示注入

提示注入是外部数据伪装成指令，诱导模型泄露信息或调用工具。防护不能只靠一句“忽略恶意指令”：

- 区分系统规则、用户输入和外部数据。
- 工具执行前做参数校验和权限检查。
- 不把密钥、完整系统提示和敏感数据暴露给模型。
- 对网页、文件和工具结果做来源标记。
- 高风险操作需要人工确认或二次验证。

## 9. Agent 是一个受控循环

```text
观察 → 计划 → 选择工具 → 执行
 ↑                         │
 └── 未完成且预算允许 ←────┘
```

普通聊天只产生文本；Agent 的输出会影响外部世界。因此必须有状态、预算、权限和停止条件。

### 9.1 工具调用

工具不是“给模型一个 URL”。每个工具需要：

- 名称和用途说明。
- 参数 schema、类型、范围和必填项。
- 返回值 schema 与错误码。
- 权限、租户和资源边界。
- 超时、幂等、重试和取消。
- 是否高风险、是否需要确认。

工具结果应精简并带状态。把整个数据库响应塞回模型既昂贵又容易让模型忽略关键字段。

### 9.2 规划

复杂任务可以拆成计划、执行、检查，但不必让模型自由生成无穷步骤。更可靠的方式是：

- 明确目标与完成条件。
- 限制最大步骤和工具调用次数。
- 使用可验证的中间结果。
- 遇到缺信息时询问或停止。
- 把长任务拆成可重试的小任务。

### 9.3 记忆

记忆可以分为：

- 当前任务上下文。
- 会话状态与用户偏好。
- 可检索的长期知识。

记忆越多，越要处理隐私、过期、冲突和删除。用户说“忘记这个”时，系统必须能找到并删除对应记录。

### 9.4 失败与预算

Agent 常见失败：

- 工具参数错误。
- 循环重复同一动作。
- 依赖超时后无限重试。
- 上下文被工具输出塞满。
- 误把不可信内容当指令。
- 无法判断任务已完成。

系统应设置最大步数、最大 token、最大时长、最大并发和最大成本。失败分类为可重试、不可重试、需要用户输入和需要人工审批。

## 10. MCP 与 A2A

**MCP（Model Context Protocol）**旨在统一主机/模型与工具、资源、提示之间的发现和调用方式，减少每个应用重复接入工具的成本。

**A2A（Agent-to-Agent）**关注不同 Agent 之间怎样声明能力、委派任务和交换结果。

协议解决互操作，不自动解决：

- 身份与授权。
- 数据隔离。
- 幂等和重试。
- 版本兼容。
- 成本和速率限制。
- 工具调用的审计。

接入协议时仍要按普通网络服务设计安全边界。

## 11. AI 原生应用不等于聊天框

| 交互模式 | 适合 | 关键设计 |
| --- | --- | --- |
| 问答 | 知识查询 | 引用、无答案、追问 |
| Copilot | 辅助编辑或操作 | 建议可接受/撤销、用户控制 |
| 工作流 | 固定多步任务 | 状态、重试、人工检查点 |
| Agent | 开放多步任务 | 计划、预算、权限、审批 |
| 后台自动化 | 定期或事件触发 | 幂等、审计、失败隔离 |

界面应显示系统正在做什么、用了哪些证据、是否需要确认，并支持取消和恢复。不要用持续旋转的“思考中”掩盖所有错误，也不要把不可逆操作藏在自动流程里。

## 12. RAG 和微调怎样选

| 问题 | 优先 RAG | 优先微调 |
| --- | --- | --- |
| 知识经常变化 | 是 | 否 |
| 需要引用和权限过滤 | 是 | 仍需外部权限 |
| 固定格式或风格 | 先试提示与少量示例 | 有大量稳定样本时可考虑 |
| 新领域推理模式 | 检索可辅助 | 高质量领域数据可能更有效 |
| 降低延迟和成本 | 评估检索成本 | 小模型可能更省 |

多数系统应先从提示、检索和工具开始，因为可更新、可解释、回滚快。微调不是把公司知识塞进模型的默认方式。

## 13. 安全、隐私与可观测性

- 检索在权限过滤后进行，生成后再次检查。
- 不把密钥、系统提示和无关用户数据提供给模型。
- 工具权限按任务最小化，写操作需要确认。
- 记录输入、检索、工具、输出和版本，但脱敏敏感数据。
- 对提示注入、越权、数据泄露、无限循环和成本异常做测试。
- 支持取消、回滚、重放和审计。

## 检查清单

- 文档解析、分块和 ACL 是否可靠。
- embedding 和索引是否版本化，更新后是否重建。
- 是否使用混合检索和 rerank，是否评估召回率。
- 证据是否可追溯到具体文档与片段。
- 无证据时是否能诚实拒答。
- 上下文预算是否为输出留空间，是否处理压缩与缓存。
- 工具是否有 schema、权限、幂等、超时和错误分类。
- Agent 是否有最大步数、成本、时间和停止条件。
- 是否覆盖检索、生成、工具和注入攻击评测。
- 取消、回滚、重放和审计是否可用。
