EasyVibe 附录第一章覆盖从晶体管到编译器的很多主题。对 AI 研发工程师来说，不需要把每个主题都学成专业课，但需要一张能定位问题的系统地图。

## 一张分层图

```
应用 / Agent
    │
语言运行时 / 编译器
    │
操作系统：进程、内存、文件、网络
    │
硬件：CPU、GPU、内存、磁盘、网卡
    │
网络：IP、端口、TCP/UDP、HTTP
```

| 层 | 核心问题 | 与 AI 工程的关系 |
| --- | --- | --- |
| 硬件 | 计算和访问有多快 | 推理延迟、显存、量化、批处理 |
| 操作系统 | 程序怎样被调度和隔离 | 超时、并发、容器、沙箱、文件句柄 |
| 编码 | 字节怎样表示文本和数字 | UTF-8、JSON、token、浮点误差 |
| 网络 | 数据怎样跨机器移动 | API、流式响应、超时与重试 |
| 数据结构与算法 | 数据怎样组织、操作多贵 | 索引、队列、检索、上下文选择 |
| 语言与类型 | 代码怎样变成可执行行为 | TypeScript、Python、运行时校验 |

把一次开机压缩成一条线：固件（UEFI）→ 启动加载器 → 内核 → 用户态 init → 登录/桌面 → 网络 → 浏览器。这里不需要展开每条指令，但出问题时要知道是“机器没启动”“系统服务没起来”“网络不通”，还是“应用自己报错”。

再往下，晶体管作为开关组成逻辑门，逻辑门组合成 ALU、寄存器和控制电路，最后形成 CPU。这一层只需要知道“计算最终是电信号和指令”，不必展开电路设计。

## 程序、进程和操作系统

源代码只是文本。程序启动后变成进程，拥有自己的虚拟地址空间、打开的文件、网络连接和线程。CPU 执行指令，内存提供工作区，磁盘和网络则慢得多。

虚拟内存通过页表把进程看到的地址映射到物理内存，文件系统把目录、inode、权限和数据块组织起来。这样进程才不用关心数据实际在哪块磁盘、哪个物理地址上。

三个直接后果：

- 频繁访问磁盘、网络或大对象，通常比多写几行计算代码更贵。
- 进程之间默认隔离；共享内存、文件和端口需要显式设计。
- 线程能并发，但共享可变状态需要锁或其他同步机制。异步不自动等于并行。

GPU 擅长大量相似计算，适合矩阵和向量运算，不适合充满分支和系统调用的任务。模型推理的瓶颈可能来自显存、批大小、数据传输或调度，而不一定是“算力不够”。

## 比特、文本和数字

计算机只存字节。文本通过 UTF-8 等编码变成字节；图片、音频和模型权重也都有各自的二进制格式。

浮点数有精度限制。金额、计数和需要精确比较的值不要随意用二进制浮点；对外传输的 JSON 数字也可能在语言之间发生精度或类型变化。

对 AI 系统尤其要注意：模型看到的不是“字符串”，而是 token；上下文长度、token 计费和截断都发生在这个转换之后。字符数不等于 token 数。

## 网络和协议

网络把消息拆成包，经 IP 找到主机，再经端口找到进程。TCP 提供有序、可靠的字节流；UDP 不保证送达；HTTP 在传输之上定义请求、响应、方法、状态码和头部。

- 延迟是往返和排队时间，带宽是单位时间能传多少数据。
- 超时、重试和幂等性必须一起考虑，否则一次失败可能变成多次副作用。
- 内网、公网、代理和防火墙都是真实边界，不能假设“本机访问”等于“线上访问”。

## 数据结构与算法

| 结构 | 擅长 | 常见代价 |
| --- | --- | --- |
| 数组 | 顺序访问、紧凑存储 | 中间插入删除昂贵 |
| 链表 | 频繁插入删除、长度变化 | 随机访问差，指针和缓存开销 |
| 哈希表 | 按 key 快速查找 | 无序、可能冲突、内存开销 |
| 栈 | 调用、解析、撤销等后进先出流程 | 不适合按 key 查找 |
| 树 | 范围查询、有序访问 | 平衡和维护成本 |
| 图 | 关系和多跳查询 | 遍历和存储复杂 |
| 队列 | 异步任务、解耦 | 积压、重复消费、顺序问题 |

算法复杂度描述输入变大时成本怎样增长。实际系统还要考虑常数、内存局部性、网络和并发。对 Agent 来说，上下文选择、工具调用次数和检索范围往往比某个排序算法更影响总成本。

二分查找每次排除一半，是“有序数据快速定位”的基本例子；排序把无序变成可比较、可检索的顺序。工程里通常直接用标准库，但要知道它们依赖有序性、比较规则和额外内存。

## 语言、编译和类型

编译型语言通常在运行前把源码变成机器码或中间码；解释型语言由运行时逐段执行。实际边界越来越模糊，JIT、字节码和 AOT 都会出现。

类型系统能在编译期发现一部分错误，但类型标注不会验证运行时数据。TypeScript 的类型在运行时基本消失；Python 的类型提示也需要工具或框架执行。网络输入、模型输出和配置文件仍然必须做运行时校验。

编程范式不必背成定义：命令式描述步骤，面向对象把数据和行为放在边界内，函数式强调纯函数和不可变数据，声明式描述目标。一个项目往往混用多种范式。

| 类型维度 | 常见选择 | 工程后果 |
| --- | --- | --- |
| 静态 / 动态 | 编译期检查 vs 运行时决定 | 静态类型更早报错，动态类型更灵活 |
| 强 / 弱类型 | 是否允许危险的隐式转换 | 它和“静态/动态”不是同一组概念 |
| 类型推断 / 泛型 | 少写标注、复用结构 | 降低重复，但复杂类型也会增加理解成本 |

编译器通常经过词法分析、语法分析、AST、优化和代码生成。不需要会写编译器，但理解 AST 后，读 ESLint、Babel、SQL 解析和模型输出解析都会容易很多。

## 这一页真正要记住什么

1. 先确定问题在哪一层，再选工具。
2. 计算、内存、磁盘和网络的速度差很大。
3. 进程、端口、文件和权限都是操作系统资源。
4. 文本、数字和二进制之间会发生转换，边界处要验证。
5. 类型检查不能替代运行时校验。
6. 对 AI 系统，token、上下文和并发预算也是资源。
