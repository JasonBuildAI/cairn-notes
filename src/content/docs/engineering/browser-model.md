---
title: 浏览器与前端运行模型
description: 理解浏览器如何把 HTML、CSS、JavaScript 和网络请求变成可交互页面。
---

前端不只是把接口数据显示在页面上。它还负责处理异步、失败、权限和用户状态。先弄清浏览器实际在做什么，再谈框架会容易很多。

## 1. 从文本到像素

| 阶段 | 输入 | 结果 |
| --- | --- | --- |
| 解析 HTML | HTML 文本 | DOM 树 |
| 解析 CSS | 样式表 | CSSOM |
| 构建渲染树 | DOM + CSSOM | 可渲染节点 |
| 布局 | 渲染树 + 尺寸规则 | 每个元素的位置和大小 |
| 绘制 | 布局结果 | 待绘制的像素指令 |
| 合成 | 图层 | 最终屏幕画面 |

```
HTML → DOM
CSS  → CSSOM
DOM + CSSOM → 渲染树
渲染树 → 布局 → 绘制 → 合成
```

修改宽高、字体或插入元素可能触发重新布局；只改颜色通常只触发重绘；只改合成层上的变换可能跳过前两步。不要凭感觉优化，先用浏览器 Performance 面板确认成本在哪里。

## 2. JavaScript 是单线程调度，不是单线程世界

```
调用栈 → 当前任务结束 → 清空微任务
       → 浏览器有机会渲染 → 下一个任务
```

网络、定时器和输入事件由浏览器其他部分处理，完成后把回调排入队列。所以 `fetch` 不会让页面停止响应，但一段很长的同步循环确实会卡住渲染和输入。

几个实际影响：

- `await` 后面的代码要等当前微任务清空后才可能继续。
- 大量小任务和频繁渲染会互相争抢主线程。
- 解析大 JSON、渲染超长 Markdown、同步处理图片都可能阻塞界面。
- Web Worker 适合把 CPU 密集任务移出主线程，不适合直接操作 DOM。

## 3. JavaScript 的四个必会语义

| 语义 | 要记住什么 | 常见坑 |
| --- | --- | --- |
| 值与引用 | 基本类型按值传递，对象和数组共享引用 | 修改“副本”时意外改到原对象 |
| 作用域与闭包 | 函数会保留它创建时能访问的变量 | 循环里的回调拿到了最后一次变量 |
| `this` | 取决于调用方式，箭头函数不绑定自己的 `this` | 把方法拆出来单独调用后上下文丢失 |
| 异步错误 | `Promise` 被拒绝时要 `catch` 或 `try/await` | 请求失败但界面一直停在“生成中” |

数组的 `map`、`filter`、`reduce` 适合表达转换，但不要为了“函数式”把复杂流程压成一行。事件处理要清理监听器和定时器；频繁绑定用事件委托。DOM 是浏览器接口，不是普通 JavaScript 对象，跨线程时不能随便传递。

浏览器和 Node.js 都运行 JavaScript，但提供的宿主能力不同：浏览器有 DOM、窗口和页面事件，Node 有文件、进程和网络服务 API；同一个库未必两边都能用。

## 4. 一次页面请求经过什么

```
URL
 │
 ├─ 浏览器缓存 / Service Worker
 │
 ├─ DNS 解析
 ├─ TCP 连接
 ├─ TLS 握手（HTTPS）
 ├─ HTTP 请求
 ├─ 反向代理 / 服务端
 └─ 响应 ──► 解析 ──► 布局 ──► 绘制
```

状态码正常不代表页面正确：可能是旧缓存、错误的内容类型、跨域拦截，或者脚本在拿到响应后抛错。排查时同时看 Network、Console 和 Performance，而不是只盯服务端日志。

## 5. JS 与 TypeScript 的边界

| 项目 | JavaScript | TypeScript |
| --- | --- | --- |
| 检查时间 | 运行时 | 编译时为主 |
| 类型信息 | 运行时值 | 编译后基本被擦除 |
| 能防什么 | 无静态保证 | 拼写、结构、部分调用错误 |
| 防不住什么 | 类型错误、空值 | 网络返回、用户输入、JSON 的真实形状 |

类型断言 `as SomeType` 只是告诉编译器“相信我”，不会校验数据。所有外部输入都应在运行时验证：

```ts
const raw: unknown = await response.json();
// 检查字段、类型和取值范围，再交给业务代码
```

这条边界对 AI 应用尤其重要：模型输出经常是“看起来像 JSON 的文本”，不是可信的结构化数据。

## 6. HTML 和 CSS 的关键约束

- 优先使用有语义的元素：按钮就用 `button`，导航就用 `nav`，不要全用 `div`。
- 布局优先掌握 Flexbox 和 Grid，知道盒模型、溢出、最小宽度和响应式断点即可。
- 可访问性不是最后补的标签：键盘能否操作、焦点是否可见、表单是否有标签，都要在结构里解决。
- 不要用颜色单独表达状态；不要阻止浏览器缩放。

## 7. 图形、动画与渲染成本

| 技术 | 适合 | 注意 |
| --- | --- | --- |
| CSS transition / animation | 状态反馈、进入退出、轻量位移 | 优先改 `transform` 和 `opacity`，避免反复触发布局 |
| SVG | 图标、矢量图、可缩放交互 | 节点很多时仍会带来 DOM 成本 |
| Canvas 2D | 大量对象、粒子、实时绘制 | 自己做命中检测、缩放和可访问性替代 |
| WebGL / WebGPU | 3D、复杂着色和大规模 GPU 绘制 | 上下文丢失、显存、兼容和调试成本 |

浏览器通常以约 60 帧/秒为目标，一帧预算约 16.7 毫秒；这包含脚本、样式、布局、绘制和合成。连续动画用 `requestAnimationFrame`，不要用一串不受控的定时器。先量 Performance，再判断瓶颈在 JavaScript、布局还是绘制。

动画应该帮助用户理解状态变化，而不是拖慢操作。提供减少动态效果的适配（`prefers-reduced-motion`），不要把关键信息只放在动画里。本站正文不使用动画或交互演示，原因也在这里：阅读、搜索和复习比视觉效果重要。

## 8. 与 AI 应用直接相关的三点

**流式输出。** 服务端持续返回增量文本时，前端要处理分块、半截 Markdown、重连和取消。一次读取不等于一条完整消息。

```ts
const controller = new AbortController();
const response = await fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ message: 'hello' }),
  signal: controller.signal,
});

// 用户点击停止时
controller.abort();
```

**不可信内容。** 模型输出、用户输入和第三方 Markdown 都可能包含 HTML 或脚本。渲染前做白名单清洗，并配合 CSP，不能因为“是模型说的”就信任。

**长任务。** 上下文很长、消息很多时，整页重渲染会拖慢输入。把增量内容批量合并，保持消息身份稳定，再配合虚拟列表和可见性策略。
