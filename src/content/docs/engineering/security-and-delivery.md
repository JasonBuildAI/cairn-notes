---
title: 安全、开源与技术交付
description: 从 Web 攻击面到工具权限、许可证和技术文档，守住 AI 系统上线前的边界。
---

安全不是上线前加一个扫描器。它要求先画出资产、入口和信任边界，再逐层限制访问；交付也不是“部署成功”，而是确认可观测、可回滚、可追溯。

## 1. 先做威胁模型

最少问四件事：

1. 要保护什么：账号、密钥、私有文档、支付能力、内部网络。
2. 谁能进入：浏览器、API、上传文件、第三方回调、模型工具。
3. 信任在哪里变化：从用户到服务、从服务到数据库、从模型到工具。
4. 最坏后果是什么：数据泄露、越权操作、资金损失、不可用、错误决策。

把系统画成数据流图，在每个跨边界处标出身份验证、输入校验、权限检查和审计。没有边界的“内部服务”最容易成为默认信任区。

## 2. 常见 Web 攻击面

| 风险 | 原理 | 基本防线 |
| --- | --- | --- |
| XSS | 恶意脚本被当作页面内容执行 | 输出编码、白名单清洗、CSP |
| SQL 注入 | 输入拼接进查询改变语义 | 参数化查询、最小数据库权限 |
| CSRF | 借用户已登录状态发起跨站请求 | SameSite Cookie、CSRF token、Origin 校验 |
| SSRF | 服务被诱导访问内网或元数据地址 | 出口允许清单、禁止任意 URL、隔离网络 |
| 越权 | 只鉴权没检查资源归属 | 每次访问验证租户/对象 ACL |
| 命令注入 | 输入进入 shell 命令 | 避免 shell，参数白名单，最小权限 |

输入校验要区分语法和业务含义。例如“URL 格式正确”不代表可以访问任意地址；“JSON 结构正确”不代表字段值安全。

密码用专用哈希算法并加盐，不自己设计加密。会话、Cookie 和令牌设置合理过期、作用域和 HttpOnly/Secure。错误信息不要泄露堆栈、SQL、内部路径或密钥。

## 3. 密钥和敏感数据

密钥不应出现在：

- 源码、提交历史、Docker 镜像、前端包；
- 提示词、模型上下文、日志和错误上报；
- 截图、演示数据和工单附件；
- 共享给整个团队的长期高权限账号。

使用环境变量或密钥服务只是第一步。还要做最小权限、按环境隔离、定期轮换、访问审计和泄露撤销。日志中记录“使用了哪个密钥 ID”，不要记录密钥值。

PII 要最小化采集，明确用途、保留期限和删除方式。向量库也可能保存可反推出敏感信息的 embedding，不能因为“不是明文”就忽略保护。

## 4. AI 特有攻击面

| 边界 | 风险 | 工程措施 |
| --- | --- | --- |
| 提示词 | 指令注入、角色覆盖 | 数据/指令分层、工具权限、输出校验 |
| 检索内容 | 恶意文档引导工具调用 | 来源标记、内容清洗、权限过滤 |
| 模型输出 | 伪造 JSON、危险命令、泄露 | schema 校验、白名单、人工确认 |
| 工具 | 越权读写、重复执行、外发数据 | 最小权限、幂等键、审批和审计 |
| 代码执行 | 逃逸、资源耗尽、访问内网 | 沙箱、CPU/内存/时间限制、网络隔离 |
| 多租户 | 检索或缓存串租户 | ACL、租户键、隔离索引与缓存 |
| 供应链 | 恶意依赖、模型或插件 | 锁定版本、校验来源、SBOM、扫描 |

提示词不能替代权限系统。如果模型进程持有删除数据库的凭据，要求它“不要删除”不是安全边界。有效的方案是它根本拿不到这个凭据，或只能通过需要审批的受限工具执行。

## 5. 安全交付流程

```text
设计威胁模型
  → 依赖与密钥扫描
  → 单元/集成/安全测试
  → 构建可追溯产物
  → 灰度发布
  → 监控与告警
  → 事故响应与复盘
```

上线前检查：

- 依赖是否锁定，许可证是否兼容，是否引入可疑包；
- 镜像是否最小化，是否以非 root 运行；
- 网络入口和出口是否按需要开放；
- 数据库是否启用备份和恢复演练；
- 配置是否区分环境，是否有误用生产凭据的保护；
- 安全头和 Cookie 策略是否正确；
- 关键写操作、工具调用和权限变更是否有审计。

## 6. 开源协作与许可证

常见许可证的粗略边界：

| 许可证 | 主要特点 | 注意 |
| --- | --- | --- |
| MIT / BSD / Apache-2.0 | 宽松，通常允许商业使用与修改 | 保留版权与许可声明；Apache 还涉及专利条款 |
| MPL-2.0 | 文件级 copyleft | 修改的受许可文件需按同许可开放 |
| LGPL | 库级 copyleft | 动态链接与分发方式需要具体判断 |
| GPL | 衍生作品需按 GPL 分发 | 商业闭源集成要谨慎 |
| CC BY-NC-SA | 非商业、署名、相同方式共享 | 不能把内容直接用于商业产品 |

许可证不是“仓库里有没有 LICENSE 文件”这么简单。还要看依赖树、素材、字体、模型权重和训练数据条款。引用他人内容时保留署名、版本、链接和修改说明；不确定时先问，而不是先上线。

开源协作中，Issue 应描述环境、复现、预期和实际结果；PR 应小而聚焦，说明动机、修改、测试和兼容影响。不是每个仓库都接受 PR；先读贡献指南和维护者的协作规则。

## 7. 技术选型和 ADR

选型不要只看热度。至少要比较：

- 是否解决真实问题；
- 学习、迁移、运维和招聘成本；
- 性能、可靠性、扩展性和锁定风险；
- 许可、社区活跃度、版本节奏和安全记录；
- 团队是否能在故障时理解和维护它。

ADR 记录背景、选项、决定和后果。它不是为了留下完美文档，而是防止团队在半年后重新争论同一个问题。

## 8. 技术写作也是交付物

文档要面向读者：

- README 说明项目是什么、解决什么问题、怎样验证；
- 设计文档写约束、方案、替代方案和风险；
- API 文档写请求、响应、错误、鉴权和示例；
- Runbook 写告警含义、排查步骤、升级路径和回滚；
- Commit 说明“改了什么、为什么改”；
- 注释解释不明显的设计原因，不复述代码。

文档随代码更新，示例要能运行，过期链接和版本号要清理。对外发布时遵守内容许可和隐私边界，不要把本地路径、密钥、内部截图和上游源码一起提交。

## 9. 最终交付清单

1. 需求、架构、数据流和权限边界写清楚了吗？
2. 关键路径有测试，安全与故障场景有演练吗？
3. 密钥、依赖、镜像和许可证都检查过了吗？
4. 指标、日志、trace、告警和 cost 能定位问题吗？
5. 部署可灰度，失败可回滚，数据可恢复吗？
6. 文档、变更记录和责任人明确吗？
7. 对用户来说，系统知道何时该停下、询问或拒绝吗？
