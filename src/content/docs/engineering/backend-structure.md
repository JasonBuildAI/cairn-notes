---
title: 后端结构与语言选择
description: 语言、客户端形态、分层和项目边界，怎样影响一个 AI 服务能不能长期维护。
---

技术选型没有统一答案。真正需要比较的是团队能力、运行环境、延迟、生态、部署成本和退出代价。

## 1. 后端语言看的是约束

| 语言 / 运行时 | 优势 | 适合与注意 |
| --- | --- | --- |
| TypeScript / Node.js | Web 生态好、全栈共享类型 | I/O 密集 API；CPU 重任务要拆分 |
| Python | AI 生态、实验速度快 | 推理服务、数据处理；注意 GIL 与部署依赖 |
| Go | 部署简单、并发和资源控制清楚 | 网关、队列消费者、基础服务 |
| Java / Kotlin | 成熟生态、强类型、企业支持 | 大型业务系统；启动和内存需管理 |
| Ruby / PHP / C# | Web 或企业生态成熟，交付速度快 | 关注运行时版本、部署方式和生态维护度 |
| Rust | 性能、内存安全和可预测性 | 高性能代理、运行时；开发成本高 |

不要用“语言性能排行榜”代替项目测量。AI 系统常见的瓶颈是模型调用、网络、显存、I/O 和调度，语言只占其中一部分。

## 2. 客户端与跨平台

| 方案 | 适合 | 代价 |
| --- | --- | --- |
| Swift / Kotlin 原生 | 深度系统能力、最佳体验 | 两套代码和团队 |
| React Native（TypeScript） | 业务型移动应用、复用前端能力 | 原生桥接和性能边界 |
| Flutter（Dart） | 固定设计、跨平台一致性 | 包体、原生集成和生态 |
| Electron | 桌面工具、复用 Web 技术 | 内存占用和启动成本 |
| Tauri | 轻量桌面、原生 WebView | 平台差异和 Rust 工具链 |

先看产品是否需要系统级能力、离线、硬件访问和发布渠道，再决定是否“一套代码多端运行”。

## 3. 分层让依赖方向清楚

```
HTTP / CLI / 消息入口
        │
    Controller / Handler
        │
      Service / Use Case
        │
    Repository / Adapter
        │
  数据库、模型、第三方 API
```

- 入口层只负责解析和返回，不承载业务规则。
- 业务层不直接依赖某个数据库 SDK，方便测试和替换。
- 仓储层封装持久化细节；模型和外部服务也应有适配器。
- 领域逻辑尽量是纯函数或普通对象，便于快速测试。

这不是要求每个项目都上 DDD。一个短期脚本可以只有一层；但只要出现第二个入口、第二种存储或需要替换模型供应商，边界就会开始有价值。

## 4. 项目结构按变化组织

按技术层分目录适合小项目；按业务能力分模块更适合边界清楚的中大型项目。关键不是目录名字，而是：

- 一个功能的相关代码能否在一处找到。
- 跨模块调用是否经过明确接口。
- 配置、日志、数据库和模型客户端是否集中管理。
- 测试目录是否能对应业务行为。

AI 项目常见结构可以拆为：API、Agent 编排、工具适配、模型供应商、检索、任务队列、评测和运维脚本。模型供应商适配层尤其重要，避免业务代码到处写某个厂商的请求格式。

## 5. DSL 与配置

SQL、正则、Terraform、Kubernetes YAML、查询语言和提示模板都可以看作领域语言。它们让表达更集中，也带来解析、版本和注入风险。

使用 DSL 前先问：它是否降低了表达成本？是否有清晰的错误信息？是否会被当作代码执行？是否能把用户输入拼进语法结构？如果答案不清楚，普通数据结构往往更安全。

## 6. AI 服务选型的额外问题

- 推理是否需要 GPU？能否用托管 API？
- 模型许可证、数据保留和地域限制能否接受？
- 流式响应、长连接和取消是否被框架支持？
- 供应商故障时能否切换模型或降级？
- 评测和回归能否在新版本上重复？
- 业务是否需要工具沙箱、对象存储和队列？

技术选型文档应写明：问题、约束、候选方案、比较维度、决定和退出条件。没有退出方案的选型，往往只是把风险推迟到未来。
