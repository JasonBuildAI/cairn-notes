Git 保存的是历史，调试寻找的是原因。两者的共同点是：都要能回到一个明确状态。

## 1. Git 的四个位置

| 位置 | 含义 | 常用命令 |
| --- | --- | --- |
| 工作区 | 当前文件 | `git diff` |
| 暂存区 | 下一次提交准备的内容 | `git add`、`git diff --staged` |
| 本地提交 | 带父节点的快照 | `git commit`、`git log` |
| 远端 | 另一份提交图 | `git fetch`、`git push` |

分支只是指向某个提交的可移动标签。`HEAD` 表示当前检出的位置。理解这一点后，“分支丢失”“提交不在主干”“回退会不会删代码”多数都能解释清楚。

```bash
git status
git diff
git add path/to/file
git commit -m "docs: explain request lifecycle"
git log --oneline --graph --decorate
```

这个站点是个人笔记仓库，不接受 Pull Request。提交信息只需要能说明“改了什么、为什么改”，不必模仿大型团队的流程。

协作时还要守住三件事：

- `.gitignore` 排除依赖目录、构建产物、`.env`、密钥和大模型权重；提交前用 `git status` 再看一次。
- 冲突通常来自同一段被两边修改。保留正确语义，删掉标记，运行检查后再 `git add`，不要直接选“我的版本”了事。
- 先 `git fetch` 看清远端变化，再决定合并或变基。会改写历史的选择要确认分支是否已经共享。

## 2. 调试是一条证据链

1. **复现**：记录最小输入、环境、版本和实际输出。
2. **分层**：先确定问题在界面、客户端请求、服务端、依赖还是模型。
3. **观察**：用状态码、日志、断点、trace 或资源指标验证猜测。
4. **缩小**：删除变量，构造最小复现，必要时用 `git bisect` 找引入问题的提交。
5. **修复并防回归**：补一个能稳定失败的测试，再让它通过。

“我觉得是缓存”不是结论。能指出哪个缓存键、命中了哪一层、用什么证据看到，才是结论。

常用工具可以按问题层级来选：

| 层 | 工具 | 先看什么 |
| --- | --- | --- |
| 浏览器 | DevTools 的 Console、Network、Sources、Performance、Application | 报错、请求、断点、长任务、存储和缓存 |
| 服务端 | 结构化日志、request ID、trace、profiler | 哪一段慢、哪个依赖失败、资源是否饱和 |
| 代码历史 | `git log`、`git blame`、`git bisect` | 哪次变化引入了问题 |
| 系统 | 进程、端口、磁盘、内存和网络指标 | 服务是否启动、是否被资源限制 |

不要同时打开十个面板找“异常”。先写出一个可被证伪的猜测，再选能最快证实或推翻它的证据。

## 3. 按错误类型选第一步

| 现象 | 优先检查 | 常见误区 |
| --- | --- | --- |
| 启动即退出 | 配置、端口、权限、依赖 | 反复重装依赖 |
| 类型错误 | 输入边界、空值、序列化 | 到处加 `any` 或强制转换 |
| 请求超时 | DNS、连接、代理、服务耗时 | 只加重试，不查根因 |
| 偶发失败 | 并发、锁、重试、外部服务 | 把日志删到看不见 |
| 本地正常、线上失败 | 环境差异、权限、网络策略 | 假设线上配置相同 |
| Agent 结果不稳定 | 模型采样、上下文、工具返回 | 只改提示词 |

## 4. 调试 Agent 时多记一层

普通请求之外，Agent 还需要保留：

- 模型名、参数和提示模板版本。
- 工具名、参数、返回值、耗时和重试次数。
- 每一步的消息数量、token 使用量与截断情况。
- request ID、会话 ID 和最终错误分类。

不要默认记录完整提示词、用户内容或密钥。需要排查时，优先记录结构、哈希、长度和经过脱敏的片段。

模型本身有随机性。单元测试可以替换模型返回，把“循环是否正确处理工具结果”与“模型这次答得好不好”分开验证。用固定录像回放比反复请求线上模型更稳定，也更便宜。

## 5. 给问题留一份最小记录

```text
现象：
最小输入：
预期：
实际：
环境与版本：
最近变化：
已有证据（日志 / trace / 截图 / commit）：
```

这份记录的价值在于：别人能复核，未来的自己也能看懂。调试不是把所有日志打开，而是让关键事实不被噪音淹没。
