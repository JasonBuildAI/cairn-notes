title: 系统设计方法与案例
description: 用需求、容量、接口、数据和故障模式回答系统设计题，而不是堆技术名。
---

系统设计不是画一张越复杂越好的架构图，而是说明：在给定约束下，为什么这套方案能工作，哪里会先坏，坏了怎么办。

## 1. 四步法

1. **澄清需求**：用户是谁，核心路径是什么，读写比例、延迟、一致性和可用性要求是什么。
2. **估算规模**：QPS、峰值、数据量、带宽、并发连接、成本和增长。
3. **画主链路**：入口、服务、数据、异步任务和外部依赖，先保证端到端。
4. **找瓶颈与权衡**：指出最可能失败或最先达到上限的部分，再选择缓存、分片、队列或降级。

一开始就问“用 Redis 还是 Kafka”通常没有意义。先说明它们要解决哪条约束。

## 2. 容量估算够用就好

常用近似：

- 一天约 `86,400` 秒，可以按 `10^5` 秒估算。
- 平均 QPS ≈ 日请求数 ÷ 86,400。
- 峰值 QPS ≈ 平均 QPS × 峰值系数，常见先按 3～10 倍估。
- 并发请求数 ≈ 到达 QPS × 平均处理时长。
- 存储 ≈ 单条大小 × 日新增 × 保留天数 × 副本数。

例：10 万日活，每人每天 20 次模型请求，平均 QPS 约 `2,000,000 / 86,400 ≈ 23`。峰值按 5 倍算是 115 QPS；如果每次请求持续 8 秒，同时处理的请求约 `115 × 8 ≈ 920`。这个数比 QPS 更能帮助判断连接池、工作进程和上游限流。

容量估算不追求精确，目的是发现数量级问题：10 QPS 和 10,000 QPS 是两种系统；1 GB 和 100 TB 也是。

## 3. 接口和数据模型先定义

接口至少写清楚：

- 请求、响应和错误结构；
- 鉴权、租户和权限范围；
- 幂等规则、超时和重试语义；
- 同步返回还是异步任务；
- 版本和兼容策略。

例如创建长时间 Agent 任务，可以让接口返回 `202 Accepted` 和任务 ID，再由查询接口或事件流返回进度。不要让一个 HTTP 连接无限期等待几十步工具调用。

数据模型要明确粒度、主键、索引、保留期限和删除方式。Agent 系统通常需要：会话、消息、运行、步骤、工具调用、文件、评测和审计记录。原始大对象放对象存储，可查询字段放数据库。

## 4. 常见模式只在有理由时使用

| 模式 | 解决的问题 | 引入的新问题 |
| --- | --- | --- |
| 缓存 | 重复读取、降低延迟 | 失效、穿透、脏数据、一致性 |
| 分库分表 | 单库容量或写入达到上限 | 路由、跨片查询、迁移和事务 |
| 消息队列 | 削峰、异步、解耦 | 积压、重复、顺序和运维 |
| CDN | 静态内容靠近用户 | 缓存键、回源和失效策略 |
| 读写分离 | 读多写少 | 复制延迟、读己之写 |

先把单库和主链路做正确。只有当指标证明瓶颈存在时，再引入相应复杂度。

## 5. 用故障模式检验设计

对每个组件问：

- 请求超时后，调用方会做什么？
- 重试是否会重复扣费或重复执行工具？
- 缓存挂了，数据库能否承受回源？
- 队列积压时，哪些任务可以暂停？
- 模型服务限流时，用户看到什么？
- 数据库主节点失败，多久能恢复，丢多少数据？
- 新版本有 bug，怎样停止扩大并回滚？

可靠性不是“所有组件永不失败”，而是失败被限制在可接受范围内。

## 6. AI 服务设计练习

需求：为多个团队提供文档问答 Agent。用户可上传文档，系统检索相关内容，调用模型回答并记录引用；部分用户允许调用内部搜索与工单工具。

约束：回答首 token 的 P95 小于 2 秒，检索结果必须带权限过滤，单租户每日有 token 预算，工具写操作必须人工确认。

```text
浏览器
  │ HTTPS
  ▼
API 网关：鉴权 / 限流 / 租户
  │
  ├─ 会话与任务 → PostgreSQL
  │    ├─ 解析队列 → 对象存储
  │    │             → 索引任务
  │    └─ Agent 运行
  │         ├─ 检索（ACL + rerank）
  │         ├─ 模型网关（预算/超时）
  │         └─ 工具（确认/审计）
  └─ 监控 / trace / 评测 / 审计
```

关键设计：

- 上传后异步解析，API 不等待整份文档处理完。
- 向量检索前先按租户和 ACL 过滤；不能先召回再“希望模型忘记”无权内容。
- 模型网关统一记录模型版本、token、延迟和错误，并执行预算。
- 工具调用分为读和写。写操作返回待确认状态，确认后才执行。
- 流式响应可取消；客户端断开后应停止后续模型调用或工具步骤。
- 评测集覆盖回答正确性、引用支持度、权限隔离、工具选择和成本。

容量上，若 1 万日活、每人 10 次问答，平均约 1.2 QPS。峰值按 8 倍是 9.6 QPS；每次模型请求 P95 为 12 秒，则同时占用约 115 个流式请求。这个规模可能一台主服务加少量副本就够，不需要先拆成几十个微服务。真正的瓶颈更可能是模型配额、文档索引速度或长连接数量。

## 7. 用 ADR 记录为什么这样选

架构决策记录（ADR）不必很长：

```text
标题：文档检索采用混合检索
背景：纯向量召回漏掉精确编号，纯关键词无法处理同义表达
决定：先并行召回，再按权限过滤和 rerank
替代方案：升级更大的 embedding 模型
后果：增加一次检索与排序成本；需要维护评测集和索引版本
```

ADR 的价值是保留上下文。几个月后有人看到复杂实现，能知道它解决过什么问题，也能在新约束出现时判断是否该改。

## 8. 上线和演进

1. 灰度发布，按租户或流量比例切分。
2. 对照关键指标：成功率、P95、成本、工具错误和安全拦截。
3. 数据迁移先双写或回填，再切读，最后清理旧路径。
4. 准备回滚开关，但不要用开关长期掩盖设计问题。
5. 每次事故和评测失败都进入回归用例。

系统设计最终要落到可观测、可回滚、可验证。图只是表达方式，证据和约束才是核心。
