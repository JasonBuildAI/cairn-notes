---
title: 请求、接口与鉴权
description: 从一个 HTTP 请求出发，理解框架、API 风格、数据格式和身份边界。
---

后端最基础的工作，是接收请求、验证身份、执行业务逻辑并返回可解释的结果。框架只是把这些步骤组织起来。

## 1. 一次请求怎样被处理

```
客户端
  │  URL + 方法 + 头部 + 请求体
  ▼
DNS / TLS / 入口代理
  │
框架：中间件 → 路由 → 控制器
  │
业务服务 → 数据访问 → 外部依赖
  │
响应：状态码 + 头部 + 响应体
```

中间件通常负责日志、请求 ID、鉴权、限流、压缩和异常处理。控制器解析输入，业务层决定做什么，数据层负责读写。把数据库查询、权限判断和响应拼装全塞在控制器里，短期快，长期很难测。

## 2. HTTP 的重点不是背状态码

| 概念 | 要理解什么 |
| --- | --- |
| 方法 | `GET` 读取、`POST` 创建或提交、`PUT/PATCH` 更新、`DELETE` 删除；语义会影响重试和缓存 |
| 状态码 | 2xx 成功、3xx 转移、4xx 客户端问题、5xx 服务端问题 |
| 头部 | 内容类型、认证、缓存、追踪、内容协商 |
| 幂等性 | 同一请求重复执行，业务结果是否只发生一次 |
| 连接 | 长连接、流式响应、超时和取消都会影响客户端体验 |

超时和重试放在哪一层要明确。一个非幂等的创建请求被自动重试两次，可能产生三份数据。写操作使用幂等键或唯一约束，读操作才更容易安全重试。

## 3. 框架和 API 风格

Web 框架通常提供路由、中间件、请求解析、响应序列化和生命周期钩子。不同语言框架的差异不如“输入校验、错误边界、依赖注入和可测试性”重要。

| 风格 | 适合 | 注意 |
| --- | --- | --- |
| REST / JSON | 资源型接口、通用集成 | 资源命名、状态码、分页和版本 |
| GraphQL | 客户端需要灵活选择字段 | 查询复杂度、缓存和权限粒度 |
| gRPC / Protobuf | 服务间高性能调用、强 schema | 浏览器兼容、调试和版本演进 |
| 文件 / 流 | 上传下载、模型流式输出 | 范围请求、背压、断点续传 |

API 设计先写清契约：输入字段、必填与范围、成功响应、错误码、分页方式、幂等语义、权限和速率限制。接口文档如果和真实行为不一致，比没有文档更危险。

## 4. 序列化与版本

JSON 可读、生态广，适合公开 API；Protobuf 更紧凑、有 schema，适合内部高频调用；MessagePack 等格式在特定场景可减少体积，但会牺牲可读性和调试便利。

无论选什么格式，都要考虑：

- 字段新增是否向后兼容。
- 枚举增加值后旧客户端怎样处理。
- 时间、金额和大整数的精度。
- 未知字段是忽略、拒绝还是保留。
- 错误响应是否包含稳定的机器可读 code。

## 5. 认证与授权

**认证**回答“你是谁”，**授权**回答“你能做什么”。两者不能混在一起，也不能只靠前端隐藏按钮。

| 方案 | 适合 | 主要注意点 |
| --- | --- | --- |
| Session + Cookie | 传统 Web、同源应用 | `HttpOnly`、`Secure`、`SameSite`、CSRF |
| JWT / Bearer Token | 服务间调用、短期凭据 | 过期、受众、签名算法、撤销困难 |
| OAuth / OIDC | 第三方登录、委托授权 | scope、回调地址、state、最小权限 |
| API Key | 机器调用、低风险内部接口 | 轮换、限流、不要放在前端 |

后端要在每个受保护资源上检查对象级权限，不能只验证“已登录”。CORS 是浏览器访问策略，不是身份认证；隐藏字段也不是安全控制。

## 6. 错误也要有契约

稳定的错误结构通常包含：机器可读的 `code`、面向人的 `message`、可选的字段错误和 `requestId`。生产环境不要返回堆栈、SQL、内部主机名或密钥。

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "请求过于频繁",
    "requestId": "req_123"
  }
}
```

对 AI 接口，还要定义流式响应中断、模型超时、内容过滤和部分结果的语义。客户端必须知道“已经生成一半后失败”应该保留、重试还是丢弃。

## 7. 一页检查表

1. 输入在边界处校验，错误可定位。
2. 认证、授权和限流都在服务端执行。
3. 写操作有幂等策略，重试不会制造重复副作用。
4. 错误响应稳定，日志有 request ID。
5. API 版本和序列化变更可兼容。
6. 长请求、流式输出和取消行为已定义。
