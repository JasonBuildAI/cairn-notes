---
title: 数据库与数据存储
description: 从表、SQL、索引和事务出发，理解 AI 系统该把什么数据放在哪里。
---

AI 应用仍然需要可靠的业务数据：用户、会话、工具调用、任务状态、评测结果和成本记录。模型不会替我们保存这些事实。选存储前先回答四个问题：数据长什么样、怎样查询、允许丢多少、增长多快。

## 1. 关系型数据库解决什么问题

关系型数据库把数据放进表。每行是一条记录，每列有明确类型；主键保证行可被唯一定位，外键表达表之间的关系。

```sql
CREATE TABLE agent_runs (
  id            TEXT PRIMARY KEY,
  session_id    TEXT NOT NULL,
  model         TEXT NOT NULL,
  status        TEXT NOT NULL,
  input_tokens  INTEGER NOT NULL DEFAULT 0,
  output_tokens INTEGER NOT NULL DEFAULT 0,
  started_at    TIMESTAMP NOT NULL,
  finished_at   TIMESTAMP
);

CREATE INDEX idx_agent_runs_session_started
  ON agent_runs(session_id, started_at DESC);
```

这里真正重要的不是 SQL 语法，而是约束：

- 字段类型和 `NOT NULL` 把错误挡在写入阶段。
- 主键给每条运行记录一个稳定身份。
- 索引让“某会话最近几次运行”不必扫描整张表。
- 事务保证一组相关写入不会只完成一半。

## 2. 查询是声明目标，不是描述步骤

SQL 说明“要什么结果”，数据库负责选择执行方式。

```sql
SELECT session_id,
       COUNT(*) AS runs,
       SUM(input_tokens) AS tokens
FROM agent_runs
WHERE started_at >= NOW() - INTERVAL '1 day'
GROUP BY session_id
ORDER BY tokens DESC
LIMIT 20;
```

排查慢查询时先看执行计划，而不是凭感觉加缓存。常用数据库都支持 `EXPLAIN` 或 `EXPLAIN ANALYZE`：它告诉你是否走索引、扫描了多少行、在哪一步排序或连接。

## 3. 索引是用写入成本换查询速度

可以把 B+ 树索引想成一本按关键字排好的目录。没有索引时，数据库可能逐行检查；有了合适的索引，它可以直接缩小范围。

几个实际规则：

- 索引不是越多越好。每次插入、更新都可能维护索引。
- 复合索引通常遵循最左前缀；`(session_id, started_at)` 适合先按会话再按时间查。
- 区分度太低、几乎每行都相同的字段，单独建索引收益有限。
- 对列做函数计算、隐式类型转换，可能让索引失效。
- 先用真实数据量和执行计划验证，再决定优化。

对向量检索、全文检索和 JSON 查询，应确认数据库是否真的提供专用索引，而不是把问题都交给一个普通 B-tree。

## 4. 事务保护“一组操作”

事务通常用 ACID 描述：

| 特性 | 含义 | 实际例子 |
| --- | --- | --- |
| 原子性 | 全成或全不成 | 扣额度与写订单不能只完成一个 |
| 一致性 | 事务前后满足约束 | 余额不能变成负数 |
| 隔离性 | 并发事务互不看到中间状态 | 两个请求不会重复领同一张券 |
| 持久性 | 提交后不会因普通崩溃消失 | 进程重启后订单仍在 |

隔离越强通常并发成本越高。常见隔离级别从低到高是：读未提交、读已提交、可重复读、可串行化。实际选择要结合数据库实现，并明确可能出现的脏读、不可重复读、幻读或写冲突。

AI 工程里有一条重要边界：**不要把耗时几十秒的模型调用包在数据库事务里**。先创建运行记录并提交，再调用模型，最后更新结果和状态。外部网络请求不是数据库能可靠回滚的操作，应使用状态机、幂等键和补偿任务。

## 5. 查询和 schema 的常见问题

| 问题 | 症状 | 改法 |
| --- | --- | --- |
| 全表扫描 | 数据一多就慢 | 补索引，缩小过滤范围，检查类型转换 |
| N+1 查询 | 请求数随列表长度增长 | 批量查询或一次 JOIN |
| 无边界分页 | 越翻越慢，内存越来越高 | 基于游标或稳定排序键分页 |
| 大 JSON 塞主表 | 更新频繁、索引困难 | 拆出常用字段，原文放对象存储 |
| 无保留策略 | 表无限增长，备份越来越慢 | 分区、归档、TTL、冷热分层 |

## 6. 不只关系型：按访问模式选模型

| 模型 | 适合什么 | 代价或边界 |
| --- | --- | --- |
| 关系型 | 事务、强约束、复杂关联查询 | schema 变更和跨库扩展需要设计 |
| 文档型 | 结构不固定、整份读取 | 关联查询弱，容易形成难治理的大对象 |
| 图数据库 | 多跳关系、权限图、知识图谱 | 运维和多团队使用成本更高 |
| 时序数据库 | 指标、日志、持续写入与时间窗口聚合 | 不适合任意业务事务 |
| 向量索引 | 语义相似检索 | 结果近似、需要 embedding 与评测 |
| 对象存储 | 文件、图片、模型权重、原始 trace | 适合整对象存取，不适合细粒度事务查询 |

一个 AI 应用的常见组合是：PostgreSQL 保存用户、会话和运行元数据；对象存储保存大文件与完整 trace；向量索引保存可重建的 embedding；消息队列承接异步任务。每种存储只负责自己擅长的事。

## 7. 选择前的检查表

1. 主查询是什么？数据量和增长速度如何？
2. 需要事务、强一致，还是最终一致就够？
3. 哪些字段需要唯一约束和索引？
4. 删除、归档、备份和恢复怎么做？
5. 数据能否从上游重建？重建需要多久？
6. 敏感数据存在哪里，谁能访问，保留多久？

存储选型没有统一答案。能让约束清楚、故障可恢复、查询可度量，就是合适的方案。
