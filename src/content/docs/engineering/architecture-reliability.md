title: 分布式系统与高可用

---

单机程序失败通常有明确边界：进程退出、磁盘报错、请求超时。进入多机环境后，网络会延迟、消息会重复、节点状态会互相看不见，系统必须假设任何一部分随时可能失败。

## 1. 先单体，再按边界拆分

单体不是落后架构。它部署简单、调用直接、事务清晰，适合产品和团队都还小的阶段。微服务主要解决的是组织与独立变更问题，不是自动获得性能。

拆分通常发生在这些信号出现后：

- 某个模块需要独立扩容或独立发布。
- 不同业务的数据和权限边界已经清楚。
- 团队协作导致单仓库改动互相阻塞。
- 单体部署和故障影响范围成为明显瓶颈。

边界优先按业务领域（DDD 的限界上下文）划分，而不是按“一个表一个服务”。如果两个服务每次发布必须一起上线、每次请求都同步串行调用，它们很可能只是分布式单体。

从旧系统迁移可以使用绞杀者模式：先把一小块能力放到新服务，用代理或路由逐步切流，验证后再扩大范围。旧系统保持可用，风险按比例增加。

## 2. 同步调用和异步消息

| 方式 | 适合 | 代价 |
| --- | --- | --- |
| HTTP / RPC 同步调用 | 需要立即得到结果 | 上游故障直接传导，超时会占用资源 |
| 消息队列 | 解耦、削峰、后台任务 | 最终一致、重复消费、积压和顺序问题 |
| 事件流 | 多个下游订阅同一事实 | schema 演进、回放和治理复杂 |

消息至少要设计幂等消费。发送方可能重复，消费者也可能在“处理成功但确认失败”后再次收到同一条消息。业务表里的唯一键、处理记录或状态机比“相信消息只来一次”可靠。

发送数据库变更和发布消息还存在双写问题。常用做法是事务内写业务数据和 outbox 表，再由独立进程把 outbox 可靠发送出去。

## 3. CAP 讲的是分区期间的选择

CAP 指一致性（Consistency）、可用性（Availability）和分区容忍（Partition tolerance）。多机系统无法保证网络永远不分区，因此真正的问题是：发生分区时，是让部分请求失败以保持一致，还是继续响应但接受暂时不一致。

常见一致性模型：

| 模型 | 保证 | 适合 |
| --- | --- | --- |
| 强一致 | 读取总能看到最新已提交值 | 账户余额、唯一占用 |
| 因果一致 | 有因果关系的操作顺序可被观察 | 会话、评论回复 |
| 最终一致 | 停止写入后副本最终收敛 | feed、统计、索引 |
| 读己之写 | 用户能读到自己的修改 | 表单提交后的个人页面 |

不要把所有数据都设成强一致。先按业务决定“旧数据造成的最坏后果”，再选择模型、超时和补偿。

## 4. 分布式系统常见的八类麻烦

1. 网络不可靠：请求可能丢失、超时，也可能实际成功但没有返回。
2. 延迟不固定：同一调用在高峰期可能慢几十倍。
3. 局部失败：数据库正常，模型服务却已经限流。
4. 节点数量多：坏一台是常态，不是极端事件。
5. 时钟不一致：不同机器的时间不能直接用来判断事件先后。
6. 消息重复或乱序：需要幂等键和可识别的版本。
7. 并发冲突：两个请求可能同时修改同一份状态。
8. 配置漂移：测试环境与生产环境的依赖并不相同。

重试会放大部分故障。没有指数退避、抖动和次数上限的重试，可能把一次抖动变成雪崩。对非幂等操作，重试前必须有去重机制或查询结果。

## 5. 共识与分布式事务

Raft 用清晰的领导者选举、日志复制和多数派确认实现共识，适合理解“多台机器如何对一个顺序达成一致”。Paxos 解决同类问题，但更抽象。日常工程通常直接使用 etcd、数据库或托管服务，不需要自己实现，但要知道写入多数派成功才代表提交。

跨服务事务常见方案：

| 方案 | 思路 | 适用与风险 |
| --- | --- | --- |
| 2PC | 协调者先准备，再统一提交 | 强协调，但阻塞和协调者故障成本高 |
| Saga | 每步执行本地事务，失败时反向补偿 | 长流程常用，需要可重试的补偿 |
| TCC | Try 预留、Confirm 确认、Cancel 取消 | 业务侵入大，适合资源预留场景 |

补偿不是数据库回滚。邮件已经发出、模型已经调用，通常只能再执行一个业务动作来抵消。因此流程状态、幂等键、重试队列和人工处置入口都要提前设计。

## 6. 高可用指标和容灾目标

可用性常用“几个 9”表达：

| 可用性 | 一年不可用时间（约） |
| --- | --- |
| 99% | 3.65 天 |
| 99.9% | 8.77 小时 |
| 99.99% | 52.6 分钟 |
| 99.999% | 5.26 分钟 |

比数字更重要的是统计口径：哪些请求算成功，计划维护是否计入，故障发生在单区域还是全站。

容灾常看两个指标：

- **RPO**：最多能接受丢多少数据，决定备份或复制频率。
- **RTO**：故障后多久必须恢复，决定备用环境与演练方式。

主备部署成本低但切换慢；多可用区能抵抗机房故障；异地多活最复杂，还会引入跨区域一致性、流量调度和数据冲突。不要为了“看起来高可用”直接上多活。

## 7. 故障检测与恢复

健康检查要区分：

- liveness：进程是否还活着，失败时重启。
- readiness：现在能否接收流量，失败时摘除但不应重启。
- 业务健康：能否完成关键路径，例如数据库、模型和队列都可用。

故障转移必须持续演练。自动恢复常见动作包括重启、隔离坏实例、切换只读、回滚版本、关闭非关键功能和限制入口流量。所有动作都应有上限，避免控制器反复重启造成循环故障。

混沌工程是在可控范围主动注入延迟、节点故障或依赖错误，验证系统是否真的能降级。它不能代替监控和备份，只是把未知风险提前暴露。

## 8. AI 服务要额外处理什么

模型服务通常比普通内部 API 更慢，而且会动态限流。系统应准备：

- 请求超时、取消和流式中断处理；
- 有预算的重试与退避，不重复计费；
- 主模型不可用时的次级模型或明确失败；
- 队列积压时的限流、排队位置和用户反馈；
- 对工具调用写操作的人工确认或权限隔离；
- 按请求、会话和租户记录 token、耗时与成本。

“所有请求都必须调用最强模型”不是可靠性设计。把关键路径、可降级能力和预算写清楚，系统才可能在故障时继续提供部分价值。

## 9. 检查表

1. 服务边界是否与业务变化一致，是否只是把单体拆成了网络调用？
2. 每项数据选择哪种一致性，失败时如何补偿？
3. 写操作是否有幂等键，消息是否可重复消费？
4. 重试是否有限制，坏实例能否被摘除？
5. RPO、RTO 和可用性口径有没有写清楚？
6. 有没有演练过数据库、模型服务或整个区域不可用？
