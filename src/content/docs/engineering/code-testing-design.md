---
title: 代码质量、测试与设计
description: 用重构、评审、测试和边界设计让 AI 代码在变化中保持可理解、可验证。
---

代码质量不是“写得漂亮”，而是下一次修改时，别人能否理解、验证和放心上线。AI 辅助编码提高了产出速度，也放大了审查和测试的重要性。

## 1. 先识别坏味道

| 坏味道 | 常见表现 | 应先做什么 |
| --- | --- | --- |
| 过长函数 | 一个函数同时处理校验、调用和存储 | 按职责拆步骤，补边界测试 |
| 重复逻辑 | 同一规则散落在多处 | 找共同语义，而不是只抽字符串 |
| 参数过多 | 调用方靠位置猜含义 | 用有名字的对象表达输入 |
| 深层嵌套 | 大量 if/else 藏在循环里 | 提前返回、策略表、状态机 |
| 隐式依赖 | 函数内部直接读全局配置 | 通过参数或依赖注入显式传入 |
| 过度抽象 | 每层只转发一次 | 删除无收益的包装 |
| 可变共享状态 | 多处随意修改同一对象 | 明确状态所有者，减少副作用 |

坏味道不是必须立刻修的错误。只有当它阻碍当前修改、导致重复事故或让测试困难时，重构才最有价值。

## 2. 重构是在测试保护下改变结构

重构改变内部结构，不改变可观察行为。安全顺序通常是：

1. 用测试固定当前行为，包括边界和错误。
2. 小步修改，每一步都运行相关测试。
3. 先移动职责，再优化命名和性能。
4. 提交保持可回滚。

如果没有测试，先把关键行为写成 characterization test（描述现状的测试），而不是一边重写一边猜。

## 3. 代码评审看什么

优先顺序：

1. **正确性**：输入、边界、并发、错误和资源释放。
2. **安全与隐私**：权限、注入、日志、密钥和数据外发。
3. **行为兼容**：API、数据库、配置和旧客户端。
4. **测试质量**：是否覆盖真实失败路径，而不只是行数。
5. **可维护性**：命名、依赖方向、重复和隐藏耦合。
6. **风格**：最好交给格式化工具，不占用评审注意力。

评审意见应具体到场景和影响。“这里以后可能有问题”很难处理；“当模型返回空数组时，下一步会抛 TypeError”可直接验证。

## 4. 测试金字塔与测试边界

```text
          端到端测试
       集成 / 契约测试
      单元测试（大量、快速）
```

越往下越快、越稳定、越容易定位；越往上越接近真实用户，但更慢、更脆。

| 层 | 测什么 | 常见错误 |
| --- | --- | --- |
| 单元 | 纯逻辑、边界、状态转换 | 把实现细节全部锁死 |
| 集成 | 数据库、队列、HTTP、工具适配 | 只测 happy path |
| 契约 | 请求/响应 schema、错误码 | 版本变化没有兼容测试 |
| 端到端 | 关键用户路径 | 用例太多、等待靠固定 sleep |

单元测试可用 AAA 结构：Arrange 准备、Act 执行、Assert 断言。测试名称描述行为和条件，例如 `returns_timeout_when_model_exceeds_deadline`。

TDD 的红—绿—重构循环适合边界清楚、反馈快的逻辑：先写失败测试，再写最小实现，最后重构。它不是所有探索性任务的硬性流程，但能逼迫我们先把验收条件说清楚。

## 5. 覆盖率是信号，不是目标

高覆盖率可能仍然没有测错误处理；低覆盖率也可能因为大量生成代码被计算。更实用的指标包括：

- 关键模块的分支和失败路径覆盖；
- 变更行是否被测试；
- 缺陷是否在测试中复现；
- 测试运行时间与 flaky 比例；
- 每次发布后的逃逸缺陷。

圈复杂度能提示分支过多，但不能替代可读性判断。不要为了降低数字把复杂逻辑藏进更多文件。

## 6. AI 应用怎样分层测试

```text
业务逻辑（确定性、单元测试）
      │
提示渲染 / 输出解析（快照、schema 测试）
      │
模型适配器（录制回放 / 小模型替身）
      │
工具与外部系统（契约 / 沙箱集成）
      │
端到端质量（评测集、人工抽检）
```

模型输出有随机性，端到端断言“答案完全一致”通常不可维护。应把测试拆开：

- 工具参数是否通过 schema 和权限校验；
- 循环是否在最大步数停止；
- 超时、限流和无效 JSON 是否正确恢复；
- 固定模型录像下，链路状态是否符合预期；
- 真实模型评测用于质量比较，不替代单元测试。

工具测试要覆盖幂等、重复调用、部分失败和危险参数。对写操作，最好在沙箱或事务隔离环境中验证，不能直接打生产。

## 7. 设计模式解决变化，而不是展示名词

| 模式 | 适合的变化点 | 例子 |
| --- | --- | --- |
| 工厂 | 运行时选择实现 | 不同模型供应商适配器 |
| 适配器 | 统一不兼容接口 | OpenAI/本地模型/内部网关 |
| 策略 | 可替换算法或路由 | 按任务选模型、重试策略 |
| 观察者 | 事件发生后通知多个消费者 | trace、计费、审计分开订阅 |
| 装饰器 | 不改主体添加横切能力 | 超时、重试、缓存、指标 |
| 单例 | 确实只能有一个全局实例 | 谨慎使用，常带来隐藏状态 |

模式的价值是让依赖方向清楚、替换成本可控。如果只有一个实现、一次变化，直接写函数往往更清楚。不要为了“未来可能需要”提前抽象。

## 8. AI 辅助编码的验证

模型可以生成代码、测试和解释，但它不知道仓库真实上下文时很容易编造 API。使用时要：

1. 提供最小但完整的相关文件，而不是几千行噪声。
2. 让它说明假设和未确认的依赖。
3. 自己运行构建、类型检查和测试。
4. 检查依赖版本、许可证和供应链风险。
5. 对安全边界、数据写入和外部调用做人工复核。
6. 用小的可回滚提交保存每一步。

“代码能编译”不等于“业务正确”。AI 生成测试也可能只验证错误实现，必须人工看断言是否真的能抓住问题。

## 9. 交付前检查表

1. 命名和边界是否能让新人从入口追到数据？
2. 关键失败路径是否有测试，而不是只有成功路径？
3. 是否把模型随机性和确定性逻辑分开？
4. 新增依赖是否真的必要，版本和许可是否清楚？
5. 日志是否足够定位问题，又不泄露敏感内容？
6. 这次修改能否单独回滚？
