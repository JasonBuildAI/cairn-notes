## 为什么要有阶段卷

总览回答“系统由什么组成”，阶段卷回答“下一步代码怎样走、事实归谁、失败后从哪里恢复”。两者不是替代关系：

| 读法 | 适合解决的问题 |
| --- | --- |
| `00-全局地图.md` | 第一次知道目录、对象和边界 |
| `01-一次Run的一生.md` | 先获得完整生命周期直觉 |
| `02-核心机制.md`、`03-工程实战.md` | 按主题补齐上下文、工具、模型和工程 |
| 本卷阶段 0～9 | 沿源码主链逐段建立可验证的因果关系 |

## 一条贯穿全卷的大脉络

~~~text
阶段0  认识目录、配置与信任边界
  ↓
阶段1  HTTP 接单 → pending → running → terminal
  ↓
阶段2  组装 LangGraph：模型 + 工具 + middleware
  ↓
阶段3  决定模型这一轮看见什么
  ↓
阶段4  决定模型能做什么，以及在哪儿做
  ↓
阶段5  决定调用哪个模型、用哪套凭据与推理参数
  ↓
阶段6  记录、恢复、审计并证明交付
  ↓
阶段7  把同一引擎接到多渠道、多 Agent、扩展与调度
  ↓
阶段8  用测试、边界和排障守住前七层
  ↓
阶段9  自己完成一个端到端改造
~~~

一句话主线：

**`start_run → pending → try_start/running → make_lead_agent → astream → journal/checkpoint → delivery receipt → terminal`。**

## 每篇的固定读法

每篇都尽量回答四个问题：

1. 这一步拥有什么事实？
2. 谁有资格修改这个事实？
3. 失败时哪一个 journal、checkpoint 或 receipt 能证明做到哪一步？
4. 哪些已经发生的副作用绝不能重做？

## 建议节奏

- **第一遍**只读“源码主线”和“可观察链路”，建立因果。
- **第二遍**做每篇实验，至少观察一个状态、一个事件或一个失败分支。
- **第三遍**回答自测题，并用源码坐标验证，而不是背结论。
- 每完成一个阶段，在纸上补一句：“这一步的事实源是 ____，失败恢复点是 ____。”

## 全卷完成标准

你应当能够不看总览，独立解释：

- 为什么 `start_run()` 是唯一接单口，`try_start()` 又为什么必须再做一次状态迁移；
- Agent 装配时哪些东西属于“配置”，哪些东西只能由服务端注入；
- 上下文、checkpoint、journal、memory 四种“记住”的区别；
- 工具为什么必须穿过 middleware 和 sandbox，而不是直接调用宿主 shell；
- Run 中断、租约丢失、交付失败和进程重启分别由哪一层收尾；
- 渠道、定时任务和子 Agent 为什么共享同一套 Run 语义。

> 阶段 0 开始时不要急着读 worker 的每个分支。先建立“谁拥有事实”的坐标系。
